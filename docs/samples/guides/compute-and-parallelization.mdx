# Compute and Parallelization

<span className="vp-label">Real page from a user guide I own. Product name, people and other identifying details are masked.</span>

Meridian allocates compute across Notes and Sequences automatically. For a Note that supports parallel execution, you can also configure how work runs *within that Note*. The settings that help depend on the Science Note and the work it can parallelize.

| If you want to… | Start here |
|---|---|
| Run multiple auto scenarios faster | Optimize Network |
| Run route optimization sub-problems in parallel | Optimize Routes |
| Run simulation replications in parallel | Simulate Network or Simulate Routes |
| Parallelize distribution fitting work | Fit Distribution |
| Investigate a single slow optimization model | Improving Solve Performance |

## How compute is allocated

Every Note run draws from a **compute pool**: a set of servers available to your workspace. Each server is an **instance** with a fixed capacity, such as 16 cores and 128 GiB of memory. For information about creating and assigning pools, see Compute Settings.

In a Note’s Compute Settings, you can choose:

| Mode | What happens |
|---|---|
| **Shared** (default) | The Note uses available capacity. If the pool is busy, the run may slow down or queue. |
| **Reserved** | You set a minimum amount of memory and CPU. The run waits until that capacity is available and holds it for the full run. If it needs more than the reserved memory, it fails with an out-of-memory error rather than borrowing more. |

### Head and workers

For Notes that support parallel execution across instances, reserved compute can be split between a **head**, which coordinates the run, and **workers**, which perform units of work. The unit may be a scenario, sub-problem, or replication, depending on the Note.

- In **Basic** mode, the head and each worker receive the same Memory/CPU value. With **Maximum instances** set to `N`, the reservation is for one head plus `N` workers: `(N + 1) ×` the value you set.
- In **Advanced** mode, you can set Head Memory/CPU and Workers Memory/CPU separately. The head typically needs less than a worker because it coordinates the work rather than performing the modeling work. If a head is consistently needing far more than that, it's worth raising with your Meridian account team rather than treating it as expected overhead.

For a walkthrough of these settings, see Compute Settings for Science Notes.

## What each Science Note can parallelize

| Science Note | Work that can run in parallel | How to enable it | What to keep in mind |
|---|---|---|---|
| Optimize Network | Auto scenarios | **Distributed runs** and **Maximum instances** in Compute Settings | Helps with a sweep of scenarios, not a single slow model. |
| Optimize Routes | Sub-problems divided by Domicile or Time Window | **Decomposition Strategy**, **Solve Strategy**, and **Number of Cores** | At least 4 cores per sub-problem are recommended. If the problem produces only one sub-problem, parallelization does not apply. |
| Simulate Network | Replications within one scenario | **Enable Replication Run Parallelization** | Auto scenarios run sequentially. Reserving more instances does not help; cores matter. |
| Simulate Routes | Replications | **Enable Replication Parallelization** | Auto-scenario parallelism is not available. |
| Fit Distribution | Series or three internal processes, depending on configuration | **Enable Parallel Processing**, which is on by default | Enabling only the process you need, such as Distribution Fitting, often allows work to run across series instead of processes. |

:::info Two meanings of “scenario”
An **auto scenario** is a Note-level sweep across parameter sets, used by Optimize Network and Simulate Network. An **App Scenario** in a next-gen Application is a user’s working copy of data for collaborative planning. They are separate concepts.
:::

### Another way to speed up a related run

**Incremental Run** uses a previous result as a starting point and re-solves only the part of the plan that changed. It is available for Optimize Network and Optimize Routes, works within the same Note, and cannot be combined with Auto Scenarios. See Incremental Run for Optimize Network and Incremental Run for Optimize Routes.

## Plan compute for a large run

1. Run only the base scenario and check its peak memory. Add roughly a 20% buffer for your most complex scenario, then use that figure to size worker memory.
2. Round CPU up from what the base scenario used. For Optimize Routes specifically, plan for at least 4 cores per sub-problem.
3. Leave some pool memory available for other Notes. Reserving all of it for one Note can cause other runs to queue.
4. If only certain scenarios fail with an out-of-memory error, duplicate the Note, disable the other scenarios, and run a failing scenario alone to find its memory requirement.

You can check actual usage in:

| Location | What you can see |
|---|---|
| Compute Settings → **See past run usage** | The Note’s last three runs, including head and worker usage for distributed runs |
| Server Statistics | Current organization-wide runs, queued runs, active nodes, and per-run CPU and RAM |
| Run History | Historical peak RAM and CPU per run over a 24-hour window; downloadable as CSV |

### Is there a limit on concurrent solves?

There is no hard platform limit on concurrent solves. In practice, available pool memory and queuing determine how many can run at once. Memory is usually the constraint, and the amount needed depends on solver configuration, model size, and variable count.

## If the run is slow

More parallelism helps only when the Note has work it can split up. For a single slow optimization model, use Improving Solve Performance to investigate where the time is spent.

Other options described in the Note guides include:

- **Decomposition:** Optimize Network and Optimize Routes offer ways to break down a model, including Rolling Horizon, Product Decomposition, or sub-problem decomposition.
- **Scheduling:** Use Scheduled Runs to run large scenario sweeps during quieter hours.
- **Pool capacity:** If the available pool is insufficient, talk to your Meridian account team about a larger or additional pool.

Reserved compute is unavailable to other Notes sharing the pool while the run holds it. Increasing parallelism for one run can therefore increase waiting time for other runs.
