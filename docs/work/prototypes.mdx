# I prototype it before anyone builds it

<span className="vp-eyebrow">Design prototypes · 2025 to 2026</span>

**What.** Before I ask engineering to build a change to the documentation site, I build a clickable prototype of it: a working page with real content that people can click through, not a slide or a written proposal.

**Why.** A prototype settles questions that a document leaves open. Stakeholders react to what they see, not to what they imagine from a description. Engineering can estimate from something concrete. And when the idea is wrong, I find out in a review meeting instead of after a sprint.

**How.** I build them myself in HTML, CSS and JavaScript, mostly with Claude Code, using real product content so the review is about the actual reading experience. Each one answers one question. I show it to the people who will use or build it, and change it until the decision is clear.

## What this shows

Design thinking applied to documentation: framing the question, making it concrete, and getting a decision before anyone spends engineering time. Five of these six shipped or were adopted.
